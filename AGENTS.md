# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

## What this is

A CLI (`tt`, also `trapi-tools`) for exercising and analyzing TRAPI services in the NCATS Translator ecosystem. It runs hand-written query files against configurable service environments, retrieves ARS responses by PK, and runs pluggable analyses over TRAPI responses. Python 3.13 only, managed with `uv`.

## Commands

```bash
uv sync                         # install deps + create .venv
source .venv/bin/activate       # or prefix everything below with `uv run`

uv run task lint                # ruff check .
uv run task lint:fix            # ruff check --fix .
uv run task format:fix          # ruff format .
uv run task typecheck           # ty check (the `ty` type checker, not mypy/pyright)
uv run task fixup               # lint:fix + format:fix + typecheck + deptry (run before committing)
uv run task yamllint            # lint YAML (config.yaml etc.)
```

There is **no pytest / unit-test suite.** The word "test" here means something else — see below. "Running tests" means running query files with `tt test`.

## The three-meanings-of-"test" gotcha

- **`tt test`** runs **query files** (HTTP requests to TRAPI services), not unit tests.
- **`tests/`** is a *library of TRAPI response validators* — subclasses of `Test` (`tests/base_test.py`) with a static `test(httpx.Response) -> TestResult`. Query files attach these to assert things about their response. `tests/battery.py::standard_battery()` bundles the common ones; `standard_battery_2_0()` is the TRAPI 2.0 variant (adds `trapi.Structural`/`trapi.Semantic` and `kg.HasKLAT`). Version-specific 2.0 asserts live in `tests/constraints.py` (constraint honoring, `ParametersEchoed`, `CollatedIntoSingleResult`) and `tests/status.py` (`TrapiStatus`).
- **Analyses** (`analysis/`) transform a parsed response into JSON output; they are not pass/fail.

## Architecture

**CLI composition.** `trapi_testing_tools/main.py` builds one Typer app from per-command sub-apps in `trapi_testing_tools/commands/` (`test`, `analyze`, `diff`, `ping`, `norm`, `pk`, `curl`, `tunnel`). `AliasGroup` enables `"test | t"`-style command aliases. Entry point `ttt` is a hack that injects `test` as argv[1]. **`validate` and `harness` are unfinished and not registered on `main`** — their `commands/` modules still exist (`validate` is an empty stub, `harness` carries TODOs and a debug `print`) but `main.py` deliberately doesn't `add_typer` them, so the CLI doesn't advertise them; the real work lives in feature worktrees and re-registers them on merge.

**`diff` command.** `tt diff [LEFT] [RIGHT]` is a TRAPI-aware, order-insensitive diff of two responses (RIGHT reads stdin if omitted; with both files omitted in an interactive TTY, both are picked via fuzzy prompt from `responses/`, else it errors). `commands/diff.py` is the thin Typer layer; `trapi_testing_tools/diff.py` is now a **presentation/reporting layer over TOM's `diff`** (TOM 2.0), which does the diffing that this module used to reimplement by hand — the order-insensitive, delta-returning design captured in `docs/tom-smarter-diff-handoff.md` was upstreamed into TOM. **The diff is version-dispatched across TRAPI 1.6 and 2.0:** `diff_responses(…, version=…)` calls `models(version).diff(...)` (from `trapi_testing_tools.trapi_models`, resolving to `translator_tom.v1_6`/`v2_0`) — the two versions' `diff`/`Delta` APIs are identical and this module's rendering never touches version-specific fields, so only dispatch differs. `--trapi-version` picks the version; omitted, `commands/diff.py` auto-detects each response's `schema_version` (`detect_response_version`, falling back to `1.6`, warning when LEFT and RIGHT disagree) and parses **both** as one version — `load_response` is split into `read_response_bytes` + `parse_response(data, source, version)` so stdin is read once before the version is known, and a real 1.x body won't parse as 2.0 (or vice-versa), so a mismatch surfaces as a clean parse error. `diff_responses` just calls `models(version).diff(left, right, strict=…, normalize=True)`: TOM normalizes deep copies of both sides (edges re-keyed by `Edge.hash()`, all bindings/aux references remapped — arbitrary per-service edge ids stop mattering; the caller's objects aren't mutated), aligns unordered lists (results, attributes, sources, analyses, categories…) as multisets in two passes (exact `.hash()`, then a coarser diff-local identity key so a re-scored analysis / changed-value attribute pairs up and reports as **one `changed`** instead of add+remove), content-addresses `auxiliary_graphs`, and returns a flat list of typed `Delta(path, kind, left, right, locator)`. Kinds are `added`/`removed`/`changed`/**`reordered`** (a genuine reorder of an otherwise-identical model-element list — surfaced with the `⇄` marker, distinct from real changes). `diff_responses` also drops TOM's one wart: it emits a vacuous `changed` for *every* response-level extra field (`job_id`, `submitter`, …) without comparing values, so we filter `changed` deltas whose `left == right`. Two modes map to TOM's `strict`: **structural** (default, `strict=True` — every field-level change incl. attributes/provenance/score) and **identity** (`--identity/-i`, `strict=False` — short-circuits subtrees whose TRAPI `.hash()` matches, so only membership changes, deliberately ignoring attribute/provenance/**score**). This module's own job is purely rendering: `_classify` maps each delta's `path` to a report section via path-prefix (`query_graph`, `results`, `knowledge_graph.nodes`/`.edges`, `auxiliary_graphs`, else response-level `other`), and three renderers consume the grouped deltas — `render_report` (section-grouped rich summary to stderr), `render_text_report` (the **default output**: compact git-diff-style plaintext — `--- / +++` header, `@@ section counts @@` hunk headers, `+`/`-`/`~`/`⇄` lines with section-relative ` / `-joined locators; `--full` expands added/removed/changed content inline as marker-prefixed JSON blocks), and `build_report` (`--json`, machine-readable, always full, for `jq`/CI). Emitted via `handle_output`.

**`norm` command.** `tt norm [ITEMS…]` is a quick identifier lookup against Translator's SRI services — **name→CURIE** via Name Resolver (default) and **CURIE→canonical id/equivalents/category** via Node Normalizer (`--id`/`-i`). `commands/norm.py` is the Typer layer; `trapi_testing_tools/normalize.py` does the HTTP + rich rendering (the two are split so `--raw`/`-r` can emit the fetched payload without rendering). It is **ping-style quick output** — no `handle_output`/view/save/`fx`: the table renders to stderr, `--raw`/`-r` prints the service's raw JSON to stdout for piping (name single → `/lookup` list; name multiple → looped `/lookup` into a `{name: hits}` map, since the Translator-hosted Name Resolver has no bulk endpoint; id → `POST /get_normalized_nodes` `{curie: node|null}` map). Input comes from positional args → piped stdin (name = newline-split, id = whitespace-split) → interactive `InputPrompt`. Name tables default to the top 5 rows with a `+N More` hint (`-n/--limit` unset fetches 10, shows 5; passing `-n N` fetches and shows N). id mode shows a detail+equivalents view for one CURIE, a summary table for many (unmatched → "no match"). The two services are `nameres`/`nodenorm` apps in `DEFAULT_ENVS` (per-maturity URLs from the SmartAPI registry; nodenorm's test/ci use the `nodenorm-es.<tier>.transltr.io` hosts) — `-e/--environment` picks the maturity (default `test`); `_resolve_service_url` falls back to `prod` with a note if a maturity is absent.

**Three filesystem-convention plugin systems**, all discovered by `rglob` + dynamic `importlib` import (no registration):

1. **Queries** (`queries/`) — plain Python modules. Either module-level globals `method` / `endpoint` / `params` / `headers` / `body` / `tests` / `trapi_version`, **or** a `steps` list of `Query` objects (`trapi_testing_tools/types.py`) for multi-request flows. A `steps` entry may also be a `FollowUp` — a `Query` subclass whose `build(previous, history)` you implement to construct that step's `Query` from earlier steps' results (each a `StepRecord`: response + test outcomes + status); use `self.derive(**overrides)` to copy the instance's fields and change only the dynamic bits. This threads data between steps (async submit → poll, create → read). Override `repeat(previous, history)` (default `False`) to run the same step again — rebuilt from its own latest result as `previous` — until it returns `False`, e.g. poll until done. To log from `build` in step with the runner's output, print via the shared console (`from trapi_testing_tools.console import console`) rather than a bare `print`; `build`-time output is auto-styled comment-color (like the re-run hint) to read as ambient commentary. `Query`/`FollowUp` are defined in `trapi_testing_tools/types.py`. `parse_query` (`trapi_testing_tools/utils.py`) validates the shape and normalizes bodies. It also **auto-injects a default `submitter`** (`inject_default_submitter`, value from `CONFIG.submitter`, default `trapi-testing-tools`; set to `""` to disable) into any query it detects as TRAPI — gated on *both* the endpoint being a TRAPI query path (`/query`/`/asyncquery`) and the body structurally being a TRAPI envelope (a `message` with a `query_graph`) — so query files no longer need to hand-write `submitter`; an author-set `submitter` is respected, never clobbered. `tt test` positional args are query files or folders (a folder runs every query within it, recursively; expanded in `set_queries`, `trapi_testing_tools/commands/utils.py`) — e.g. `tt test queries/routine/v2_0 -e retriever.ci`. Note `.gitignore` ignores `queries/*` except `routine` and `additional`, so ad-hoc queries under `queries/working/` are local-only.
   - **TRAPI version dimension.** A query file's `trapi_version` global (`"1.6"` default, or `"2.0"`) selects which TOM model namespace its tests parse/validate against — resolved centrally in `trapi_testing_tools/trapi_models.py` (a `current_trapi_version` ContextVar the runner binds per query; `models(v)` / `semantic_validate(v)`). Author 2.0-shaped bodies (top-level `parameters`, QEdge `constraints`, COLLATE, etc.) and set `trapi_version = "2.0"`. The routine set is split by version: `queries/routine/v1_6/**` and `queries/routine/v2_0/**`; run a version by pointing `tt test` at its folder.
   - **Capability / profile organization.** Under each version, query files live in `capabilities/<capability>/` (`lookup`, `metakg`, `validation`, `constraints`, `parameters`, `set-input`, `collate`, `node-only`, `creative`, `pathfinder` — the last two are 2.0-and-ARA territory). `profiles/<profile>/` (`lookup`, `ara`, `minimal`) are **directories of symlinks to the capability dirs** a component type can run, so an owner selects one folder: `tt test queries/routine/v2_0/profiles/ara -e aragorn.ci` vs `.../profiles/lookup -e retriever.ci` (everything except creative/pathfinder). `set_queries` rglobs directory args with `recurse_symlinks=True` (Python 3.13+ skips symlinked dirs otherwise) and de-dups resolved paths (profiles overlap: `ara` ⊃ `lookup`). Capabilities are the single source of truth; profile membership is a sensible default, not a contract (a service that can't do a capability just gets interpretable failures).
2. **Analyses** (`analysis/`) — subclass `Analysis` (static `analyze(response)`) for argument-free, or `ParametrizedAnalysis` (holds a `typer.Typer` `app`; CLI args come after a `--` separator, response injected via `ctx.obj`). `discover_analyses(version)` (`commands/utils.py`) finds concrete subclasses. **The class docstring is the display name** (final period stripped). See `analysis/v1_6/path.py` for multiple analyses sharing helpers in one file. **Analyses are split by TRAPI version** into `analysis/v1_6/` and `analysis/v2_0/` (mirroring the queries); `tt analyze --trapi <ver>` (default `1.6`) scopes discovery to that version's subdir and binds the parse version, so same-named analyses across versions don't collide. `base_analysis.py` is shared.
3. **Response validators** (`tests/`) — see the gotcha section above.

**Configuration & environments.** `TTTConfig` (`config.py`, pydantic-settings) layers, in priority order: env vars (nested delimiter `__`) → `.env` → `config.yaml` → defaults. `DEFAULT_ENVS` (hardcoded ars/retriever/shepherd, plus the `nameres`/`nodenorm` identifier services `tt norm` uses) is always merged in; `config.yaml` adds/overrides (bte, aragorn). `utils.py` flattens this into `ENVIRONMENT_MAPPING` keyed by `app.level` (e.g. `bte.ci`) **plus** bare `level` keys for `default_environment` — so with the default (`retriever`), `-e ci` resolves to `retriever.ci`.

**Output & piping (important).** All rich/interactive UI writes to **stderr**; only piped payloads go to **stdout**. This is what makes `tt test ... -p plain | tt analyze NAME -p | jq` work. `OutputModes = (view_mode, save_mode)` and the shared `handle_output` (`utils.py`) drive it: view opens `CONFIG.viewer` (default `fx`, falls back to `less` for non-JSON), save writes to a path (with multiple query files/environments each response is saved under an env/path-qualified prefix, e.g. `retriever.dev.routine.metakg_resp.json`), `-p/--pipe` prints JSON to stdout. Interactive selection (fuzzy prompts via InquirerPy) is disabled in pipe mode and requires a file/args instead; **without a TTY**, view/save (and traceback) prompts are skipped, defaulting to no-view/no-save. **`tt test` piping shape is `--pipe/-p MODE`** (`report.py`, `PipeMode`; the flag requires a value): `-p plain` emits just the response body/bodies — a lone body bare so it chains into `tt analyze`, several as a JSON array; `-p report` emits one aggregate `RunReport` JSON envelope (per-query/per-step `status`/`http_status`/tests/timing/`size_bytes`, no bodies); `-p full` is that envelope *with* response bodies. `elapsed_seconds`/`size_bytes` are also aggregated at the query and run levels; bodies are in/excluded per step at build (`include_response`), the envelope built only when piping. **`-e/--environment` is repeatable** (its interactive picker is multiselect): each query runs against each environment sequentially, yielding one `queries[]` entry per (query, environment) — each stamped with its `env`, all listed under the top-level `envs`. `-d/--debug` with `--pipe` keeps responses only for failing queries. `tt test` exits non-zero if any query or test fails.

**Repeat last test (`-R`).** `tt test --repeat/-R` replays the previous invocation. After every `tt test` run the *resolved* invocation (queries as absolute paths, environment names, and the flags) is persisted as JSON to `PlatformDirs("trapi-testing-tools", "biothings").user_state_path / "last_test.json"` — see `last_run.py` (`save_last_test`/`load_last_test`). Persisting *after* `set_queries`/`set_environment` captures interactive fuzzy-picks too; `-R` re-injects those before resolution so no prompt fires (replay), while any params typed on the current line **override** the remembered ones. Override detection uses `ctx.get_parameter_source(name) == COMMANDLINE` (the only `get_parameter_source` use in the repo), **except** `queries`, a variadic argument Click always reports as `COMMANDLINE` — for it, `queries is not None` is the "was it given?" signal. A missing snapshot dimension is left `None` so the normal prompt still fires (graceful fallback); a wholly-missing snapshot with nothing typed is a friendly `Exit(1)`.

**Async queries.** `run_query` (`run_query.py`) detects `asyncquery` endpoints. By default it **receives the callback directly**: `callback.py` stands up an ephemeral local HTTP receiver, injects a per-query `callback` URL into the request body (via `dataclasses.replace`, and **only** when the body has no callback of its own — an author-set `callback` is respected and forces the poll path), then blocks until the service POSTs its response, which is wrapped as a synthetic `httpx.Response` so tests/report/output are unchanged. `CONFIG.callback.mode` (`auto`/`direct`/`tunnel`/`poll`, overridable per-run with `--callback-mode`/`--cb`) picks reachability: `auto` uses a direct `127.0.0.1` callback for loopback/private targets (`_is_local_target`) and a **cloudflared quick tunnel** for remote ones. **Direct** uses a per-run local receiver (in-process `wait`). **Tunnel** uses a detached, **global** daemon (`callback_daemon.py`, spawned via `python -m`) that holds the receiver + tunnel and is **shared by all `tt test` runs on the machine** (a single JSON state file, `tunnel.json`, in the platform state dir is the discovery/reuse handle) so one tunnel is created and reused, not one per run. It has no owning shell: it persists in the background and reaps itself after an idle period (default 1800s) or on `tt tunnel stop`. The `tt test` process awaits daemon callbacks by long-polling the daemon's local `GET /result/{token}`. `tt tunnel` shows status (and, on a TTY, prompts to start/stop); `tt tunnel start` prewarms it, `tt tunnel stop` kills it — `start` is handy on TLS-intercepting networks to create the tunnel *before* connecting a VPN (a tunnel established off-VPN survives VPN activation). **Caveat (matters when hacking on TTT across branches):** the daemon is global and *not* version-keyed — whichever run starts it first runs it with that checkout's code, and a concurrent run on a branch with a divergent callback/receiver protocol will reuse that daemon and may break. Concurrent *same-protocol* runs are safe (per-request uuid tokens keep callbacks isolated). After switching to a branch that changes the callback protocol, run `tt tunnel stop` so the next run respawns the daemon with the new code. If cloudflared is missing/fails to start, or mode is `poll`, it falls back to the legacy path — inject an unreachable placeholder `callback` (`PLACEHOLDER_CALLBACK`, so the request stays valid TRAPI since `callback` is required), then poll `asyncquery_status` every 10s until done/timeout (`CONFIG.timeout`, default 300s), then GET `response_url`. Infrastructure is lazy (all-sync/poll runs start nothing). `cloudflared` is an optional external binary (like `fx`); tunnel callbacks are capped at 100 MB by Cloudflare Free/Pro, so remote very-large responses may need `poll`. Docker/LAN local targets may need `callback.host: host.docker.internal` or `callback.bind: 0.0.0.0`. Tunnel readiness holds the query until the fresh tunnel is usable *by the remote service*, via two checks: (1) cloudflared has registered an edge connection — its `/ready` metrics endpoint (`readyConnections >= 1`; spawned with `--metrics 127.0.0.1:0`, address scraped from stderr) or the "Registered tunnel connection" log line; and (2) the hostname resolves via **public DoH resolvers (1.1.1.1/8.8.8.8)** — a DNS-propagation check that prevents the service hitting `Name or service not known` on an un-propagated hostname. Both deliberately avoid HTTP-probing the tunnel URL *and* the **local** DNS resolver, which false-negative on many networks (a host often can't reach/resolve its own fresh tunnel even though the remote service can). The URL regex excludes `api.trycloudflare.com` (cloudflared's own request endpoint, which appears in its error logs — matching it once made a *failed* tunnel look successful and produced 405s), and startup fast-fails if cloudflared exits (e.g. TLS-intercepted on a corporate network). Readiness is advisory: on timeout a scraped URL is used regardless; only a *missing* URL (cloudflared absent/failed) falls back to poll. The daemon logs to `tunnel-daemon.log` in the state dir (URL + `readiness confirmed=`, received callbacks, or the failure reason with recent cloudflared output) — the go-to place when a tunnel "is unavailable." Testing seam: `TTT_TUNNEL_URL` bypasses cloudflared (`self` = the daemon's own loopback URL).

**PK retrieval.** `tt pk` (`retrieve_by_pk.py`) fans out concurrently across all ARS instances to locate the PK, fetches the trace, prompts to pick an ARA child actor, and retrieves that ARA's stored TRAPI response. Metadata prints alongside the payload include a per-actor **merge count**, tallied by agent from the trace's `merged_versions_list` (a `repr`'d list parsed with `ast.literal_eval`, since a child's own copy is empty). `--trace/-t` skips the drill-down and outputs the whole trace with its per-actor metadata table; `--raw/-r` keeps the drill-down but skips `extract_response_payload`, emitting the raw ARS stored response instead of the TRAPI payload (`-t` takes precedence). `--triage/-T` skips the picker entirely, concurrently fetches **every** ARA child's stored response, and renders each in a `tt test`-style framed block (`run_triage`): a `┌ <actor>` rule, an `IndentedBlock` gutter around the metadata + `standard_battery()` results, and a `└` verdict line. The battery reuse is literal — it builds a synthetic `Query(tests=standard_battery())` + a rebuilt `httpx.Response` and calls `run_query.run_tests`, so the test lines match the runner exactly; `retrieve_by_pk` therefore uses the **shared** runner `console` (so the pushed `IndentedBlock` hook wraps `run_tests`' output), and `IndentedBlock` was extended to gutter `Table` too (no other command prints a table inside a block). `print_ars_metadata(..., left_align=True)` drops the title/box for the block. It is a presentation mode that ignores the view/save/pipe flags.

**translator_tom (TOM).** Query bodies may be raw dicts or TOM model objects (`serialize_body` normalizes them); analyses receive a parsed `translator_tom.Response`. TOM is imported lazily so raw-dict query authoring never loads it.

**Query-body constructors.** `trapi_testing_tools/query_utils.py` provides convenience builders for TOM query bodies: `one_hop` (a two-node/one-edge query from category/id/predicate args), `from_qg` (wrap an existing `QueryGraph`/`PathfinderQueryGraph` in a `Message`+`Query`), and `load_json` (load a JSON file as a given TOM model — a bare query graph, a `Message`, or a full `Query` — and reconstruct a complete query body). All apply a default `submitter` and pass extra keyword args through as body-level fields.

## Conventions

- Ruff is configured broadly (pydocstyle google convention, type-annotation rules, pathlib-over-os, etc.) with line length 88. Docstrings are required on public functions/classes.
- New analyses/queries/validators need no wiring — just drop a file in the right directory following the base-class contract.
